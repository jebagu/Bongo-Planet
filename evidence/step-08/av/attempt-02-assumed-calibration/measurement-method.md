CDP screencast JPEGs record actual compositor pixels. The [protocol](https://chromedevtools.github.io/devtools-protocol/tot/Page/#type-ScreencastFrameMetadata) describes each metadata timestamp as frame-swap epoch time. [Chromium implementation](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/devtools/protocol/page_handler.cc) uses the capture frame's expected display reference time, with a current-time fallback when unavailable. This measures headless compositor presentation, not physical monitor scanout or a human watching a screen.

The pixel detector uses a fixed 25×25 region around the projected original target. It detects at least three pixels with red >180, green >170 and blue >160. Before the first measured onset, frames 01482/01483 contain zero qualifying pixels and cyan note pixels; frame 01484 contains 260 qualifying pixels and the visibly bright note. Each group retains the previous nonbright and first bright image, their timestamps and the resulting onset interval. Visual timing is inferred from those pixels, never from the view's trigger callback time.

[Web Audio's output timestamp](https://www.w3.org/TR/webaudio/#dom-audiocontext-getoutputtimestamp) relates the context sample position to estimated output-device presentation performance time. Repeated timestamp pairs supply a fixed context-to-performance offset; frame epoch timestamps use the page's performance time origin. Maximum observed output-clock offset deviation was 0.102334 ms. One fixed measured loopback offset is removed before that output-presentation mapping; no fitted slope or changing correction is applied.
