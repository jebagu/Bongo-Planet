# Bongo Planet — receiver scheduling investigation

Read-only investigation of `src/output/bridge.ts`, `src/output/OutputAdapter.ts`, `docs/Output-Protocol.md`, Work-Package Steps 09/11/12, `quiet-analysis.json`, and `docs/Build-Handoff.md`. No application changes, experiments, new captures, or gate changes were made.

## Finding

The demonstrated failure is deadline execution in the receiver, after successful early delivery. Quiet F01 delivered 178/180 onsets: `s2-62` was queued 496.024 ms before its deadline and its timer callback ran 66.385 ms late; `s2-63` was queued 621.172 ms early and ran 44.642 ms late. Both were counted and dropped by the existing 20 ms guard. The associated independent-process witness interval recorded 94.263 ms heartbeat slip and 97.780 ms event-loop delay. F04 passed 420/420. Independent scheduling arithmetic and clock probes were accurate; neither explains these two misses. See [quiet analysis](quiet-analysis.json).

This supports a scheduling/service limitation of the measured configuration. It does not identify a particular OS cause or prove intrinsic hardware incapability. The witness is an independent process, so isolating work inside the current Node event loop cannot be assumed to remove the cause.

## Current contract and failure point

`bridge.ts` validates strict versioned messages, producer/session ownership, separate control/position sequences, trigger-sequence replay protection, positions-before-trigger, limits, and the onset acceptance window. At lines 30–31 it accepts a future trigger, then delegates its deadline to `setTimeout`. The callback's actual `performance.now()` determines onset error; more than 20 ms late becomes a real missing onset. HTTP rendering, WebSocket ingestion, UDP observation, JSON serialization, timer scheduling, and voice bookkeeping share the Node event loop. The Node timer API explicitly provides no exact callback-time guarantee. [Node timer documentation](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args).

Cancellation clears matching pending timers and releases matching test voices; node cancellation also removes positions. Stop invalidates the session and clears all objects/work. A 20 ms Node interval expires test voices and enforces the 500 ms receiver watchdog. Therefore the same host pause can delay both an onset and a stop/watchdog action. Moving only the onset timer leaves part of the lifecycle exposed.

The current receiver is a control demonstration, not the venue synthesizer. Step 09 requires actual receipts exactly once, correct objects/XYZ, clock uncertainty ≤10 ms and onset p95 ≤20 ms. The present late-drop policy also remains unchanged. Step 11 must select the actual synth/renderer, sample rate, route, and agreed control-to-sound limits; Step 12 qualifies the complete sound path. An improved local receiver cannot silently qualify that external path.

## Minimal substantive remedy for this reference configuration

**Keep Node as validator/UDP/HTTP infrastructure and immediately forward accepted future controls to one companion receiver browser AudioWorklet.** Replace Node's per-trigger onset timers with that worklet's actual render-frame queue. This uses the project's current browser audio stack, requires no venue synth or native build, and is a substantive but implementable M1 control-receiver change. It is a proposal, not a measured fix.

Serve a small receiver-control page under the existing application origin, for example `/BongoPlanet/receiver-clock/`. Give it an explicit “Enable receiver clock” gesture and one continuously active AudioContext. A versioned internal sink WebSocket route on the bridge registers exactly one receiver separately from the producer; do not confuse sink connection with `start`, admit a second producer, or expand the current Origin policy arbitrarily. Node forwards validated positions, triggers, cancellation, stop and heartbeat records in their accepted order. The companion page transfers them immediately to its worklet. The existing HTTP receiver can display the resulting status/receipts. No UI rendering or Node timeout determines onset execution.

The worklet maintains bounded pending/object/voice state. In each actual `process()` callback it applies incoming commands, compares the real `currentFrame` plus each sample offset with queued targets, and records an onset only at the sample index where it executes the control transition. A late event uses the first real available sample; it never reports an earlier intended sample. Records contain session, immutable trigger sequence/ID, node/generator/object, current XYZ, actual processed block and sample index. Later MessagePort/WebSocket/HTTP delivery times are retained separately. Reporting an accepted future timestamp before `process()` actually reaches it would be fabricated evidence.

The known F01 events had 496/621 ms lead at Node ingress. Immediate forwarding could put both into the receiver worklet before the host spike; this is the concrete causal benefit. Measure **worklet ingestion lead**, not only Node queue lead. A new Node→receiver transfer stall or audio underrun can still fail.

### Clock and execution evidence

There are now three clocks: producer audio time, Node monotonic time, and receiver audio frames. Keep the original producer↔Node probe and add a receiver↔Node probe. Establish a dated mapping of receiver sample frames to the receiver's monotonic performance clock, retaining uncertainty, mapping version, sample rate, quantum size, route and start/end drift. `getOutputTimestamp()` supplies an audio-context/device-presentation to performance-time relationship; it must not be confused with the ahead-of-presentation time at which a render callback computes a block. [Web Audio timestamp method](https://www.w3.org/TR/webaudio-1.1/#dom-audiocontext-getoutputtimestamp).

The implementation must name both quantities: **actual processed sample frame** and its independently calibrated **monotonic frame time**, plus delayed report arrival. Report the full combined producer↔Node↔receiver mapping uncertainty; ≤10 ms cannot mean only one leg. Compare calibrated actual frame time with the unchanged incoming deadline and reject/drop real errors over 20 ms. Retain the raw deadline and frame values so any route/mapping constant can be audited. Do not offset the deadline by a fitted delay until misses disappear.

A silent, connected worklet returning `true` with zero output and actual `process()` transitions is sufficient to investigate Step 09 control execution; use a real AudioContext, not OfflineAudioContext or a manually invoked processor. It does not prove audible output. For qualification, collect a diagnostic mode that writes identifiable impulses at those same actual sample indexes to an isolated capture route and compare them with independently calibrated timing. This validates that frame labels correspond to real rendered samples and that the mapping has not hidden callback/output buffering. Step 09 does not require a venue synthesizer; Steps 11/12 still require the actual venue route. Web Audio's render clock and frame globals are specified independently of browser-main-thread callbacks. [Web Audio rendering model](https://www.w3.org/TR/webaudio-1.1/#rendering-loop).

### Lifecycle boundaries

1. Refuse producer musical start until the sink is activated, synchronized and reporting an active clock; retain paused object snapshots. If the sink disappears, the bridge releases/invalidates the producer rather than silently reverting to Node timers. Existing fail-closed control backlog behavior remains visible.
2. Preserve 92 objects, 5,376 pending triggers, 64 voices, 12-second horizon and the 20 ms late policy. Use preallocated/bounded pending and receipt storage, keep trigger/cancel traffic reliable, and fail visibly if receipt storage overflows. Do not coalesce musical controls. Avoid unbounded work, network/file operations or blocking waits inside `process()`.
3. Process accepted control order before due sample transitions. Cancel IDs/node generations invalidate queued events and release active voices; node cancellation removes the old position, so a retained/recreated node requires its fresh position before a new trigger. Stop/session epochs invalidate all older work. Cancellation received before an unrendered onset suppresses it; a command received after a rendered sample releases it without claiming retroactive cancellation. Qualify close-deadline behavior anew.
4. Heartbeats need not use a Node callback to release the sink: the worklet owns its last valid heartbeat/frame deadline and clears queued/active state after the 500 ms policy. The page/bridge also watches context suspension and socket closure. Frame time alone freezes on suspension, so every resume must invalidate pre-suspension work and re-handshake before accepting music. Do not resume an old queue automatically. A guarded, higher-priority stop/epoch path must work when the ordinary queue is full.
5. Refresh current XYZ at onset, retain camera-independent mapping and the 50 Hz position contract, and preserve cancel→fresh-position→trigger ordering. Worklet-side pending/voice counters and receipt records become the authoritative musical receiver state; delayed HTTP refresh remains presentation.

At 48 kHz a 128-frame block is 2.667 ms, but measure the actual quantum/route rather than assuming it. Even correct sample-index scheduling can underrun. No claim of hard real-time guarantee follows merely from choosing AudioWorklet. A native Core Audio callback receiver remains a viable second implementation if the browser companion fails measured execution/lifecycle budgets; its host/sample timestamps and real-time threading also require qualification. [Apple timestamps](https://developer.apple.com/documentation/coreaudiotypes/audiotimestamp), [Apple audio workgroups](https://developer.apple.com/documentation/audiotoolbox/understanding-audio-workgroups).

## Alternatives and limits

| Option | Useful effect | Why it is not already a qualification |
| --- | --- | --- |
| Node Worker with its own timer queue | Separates JSON/HTTP work from deadline handling; smallest source refactor | Ordinary worker timers still depend on OS execution. The independent-process delay argues against treating this as a root-cause fix. Cancellation/watchdog must move with ownership, and receipts need fresh qualification. Node describes workers as parallel JavaScript, not a deadline scheduler. [Worker documentation](https://nodejs.org/api/worker_threads.html). |
| Companion browser AudioWorklet receiver — recommended local next implementation | Reuses current platform and moves queued deadline execution to a real audio render thread | Concrete architecture above; needs new receiver transport/activation, fresh frame calibration and lifecycle qualification. No guarantee against receiver-main-thread transfer delays or audio suspension. |
| Native renderer/plugin deadline ownership | Can schedule directly in the final synth/render callback and remove another downstream hop | Step 11 route, renderer grammar, platform access and device configuration remain unknown. Select that venue route with its owner; then repeat Step 12 timing and cancellation tests. |

Changing timeout intervals, swapping in `setImmediate`, adding more lookahead to these already-early packets, repeatedly retrying the same configuration, or busy-waiting is not a demonstrated remedy. Merely logging the intended onset while delivering late would falsify the measurement. Removing the guard would change the stated semantics and still leave late execution.

## Zero-delay and upstream latency remain separate

The browser commits triggers at emission, and `OutputAdapter.event(trigger)` receives them through the browser main thread before sending WebSocket traffic. **Current source passes `audio.now` to OutputAdapter; only the view uses `audio.audibleNow`.** Therefore there is no demonstrated 13 ms deliberate zero-delay network lead in the current adapter. Switching the adapter to `audibleNow` would shift deadlines by the measured output-latency compensation and is a separate clock-contract decision, not free scheduling headroom.

A zero-delay event's current target time is already at emission. No receiver can execute a packet before it arrives; moving receiver deadlines to an audio thread solves the observed early-queued callback failure, not arbitrary upstream stalls. A positive fixed remote delay or committing events before emission would change musical/animation semantics and is not proposed here.

Preserve zero-delay intent and measure its actual end-to-end receipt/execution against the same 20 ms policy. If the required zero-delay tests fail under browser-main-thread stalls, a separate producer-transport change is required: an AudioWorklet-written bounded shared-memory event queue consumed by a dedicated network worker could bypass UI-main-thread forwarding. That design needs supported cross-origin isolation, ordered cancellation/epochs, clock mapping and independent transport qualification; it still cannot defeat arbitrary OS/network delay. Alternatively, a receiver-side replicated engine would be a much larger authority/ordering redesign, not this minimal repair.

Late deletion/stop packets have the same physical limit. Qualified cancellation means the sink correctly acts on commands that reached it within the tested timing envelope, with the watchdog bounding broken connections; it cannot guarantee a remote edit whose command was never delivered. Declare and measure that envelope rather than silently changing snapshots, clocks, or deadlines.

## Required closure evidence

Before claiming repair, retain the failed captures and produce a new immutable-source qualification on the same reference environment: real two-minute F01/F04 exactly-once receipts, unchanged independent onset oracle, sample/frame execution records, fresh browser↔Node↔sink clock uncertainty/drift, actual output markers where output execution is claimed, and independent host-delay telemetry. Exercise zero-delay chords, position-before-trigger, move interpolation at 60/15/2 FPS, duplicates/stale sessions, delete/re-add and same-ID kind changes, cancel just before/after deadline, stop while Node is deliberately stalled, queue overflow, device suspension, and reconnect without replay. Verify actual pending/active release rather than only HTTP metadata. A negative test that deliberately delays sink delivery must fail visibly under the unchanged guard.

The local Node timer receiver remains failed today. The companion AudioWorklet is the minimal recommended local next implementation, with an explicit receiver clock/cancellation decision and unchanged measured budgets. It can be developed and qualified within M1 without waiting for venue hardware. Worker isolation is an optional diagnostic/refactor, not the acceptance solution. Venue rendering grammar, physical routing/latency and listening remain external M2 work; local control-clock and cancellation qualification are concrete M1 work, not external dependencies.

## Subsequent authorized standalone diagnostic

The separately authorized [receiver-clock prototype](receiver-clock-probe/Checks.md) demonstrated actual prequeued AudioWorklet execution while its own Node thread was blocked. Controls reached the processor with 496/497 ms lead; actual process/sample-index control errors were 0.001953/0.337646 ms, while existing Node timer controls were 80.279958/231.642541 ms late and dropped. Conservative calibration uncertainty was 2.867462 ms; actual frame/sample records and coarse callback wall times are preserved independently from intended timestamps and delayed Node report arrival. Small cancel/epoch/watchdog cases passed. A separate producer context startup zero-delay probe executed 10.162598 ms late without a shifted deadline; steady-state/product-forwarding behavior remains unmeasured. This adds feasibility evidence, not application receiver/F01/F04 or audible-output acceptance. No application source was changed.

## Native monotonic follow-up

The above recommendation is retained as the decision made before the live render-clock experiments. The render companion subsequently passed F01 but failed its F04 uncertainty/mapping guard; that diagnostic remains available explicitly and its failures are preserved. A separately tested native worker hypothesis demonstrated ordinary-timer numerical control execution during parent-thread stalls with independent hrtime witnesses, without audio-frame or sound claims. The production bridge now uses that native clock by default. Its fixed conversion, bounded IPC, cancellation ordering, failure lifecycle and actual isolated mutations pass the current tests and independent source review. Fresh sustained F01/F04 evidence is being gathered separately; the change does not qualify browser audio clock conversion or venue sound. See [native hypothesis review](receiver-worker-probe/Independent-Review.md) and [production integration](native-clock-integration/Handoff.md).
