## RC-01: Rebinding a node changes the coordinates of an already committed object trigger

**Confidence 100. Repaired; source readback and independent simulated-processor recheck completed below.**

The initial bridge stored objects by integer object ID and rejected an existing integer ID assigned to another node. The worklet stored objects by node ID. The reverse binding invariant was missing.

Exact sequence: start session `s`; send position `n → object 1` at `[1,0,0]`; queue trigger `s-1` for node `n`, object 1, onset 0.1; send a newer position `n → object 2` at `[0,1,0]`; advance through the onset. Both position messages passed the original Node admission checks. The worklet replaced its sole `n` entry, then emitted an object-1 onset with object-2 coordinates. The bridge's receipt checks compared the object ID to the trigger but accepted the mismatched coordinates.

An in-memory execution of the actual embedded processor reproduced `{id:'s-1', objectId:1, position:[0,1,0], actualOutputSample:0.25}` with no fatal receipt. This did not depend on a browser scheduling race. The normal product mapper preserves active bindings, but the receiver must enforce the same invariant on accepted protocol input.

Minimal repair, now present on readback: Node rejects an active node ID paired with a different object ID before mutation/forwarding; the worklet rejects that rebinding defensively. Cancelling/removing a node first permits a subsequent fresh binding. A regression should verify the original object's coordinates remain unchanged after rejecting the attempted rebind, and that cancel-then-rebind remains supported.

## RC-02: Individually valid cancellation packets amplify into an oversized receipt batch

**Confidence 100. Repaired after the initial review; source and independent simulated-processor recheck completed below.**

The initial `cancelled` receipt echoes all trigger IDs and node IDs from the accepted cancellation packet. A batch bound of 16 rows is not a byte bound. The bridge WebSocket server has `maxPayload: 128 * 1024`, while the page sends the complete JSON batch as one frame.

Concrete input: 16 sequential cancellation commands, each containing 100 distinct IDs of 128 characters and no node IDs. Each packet is schema-valid and 13,177 JSON bytes, below both 64 KiB and the server's inbound limit. The corresponding 16 echoed `cancelled` rows form a 211,003-byte batch, above the 131,072-byte receiver frame limit. They can be accumulated while an earlier receipt is awaiting acknowledgement and then flushed together. Cancellation of unknown IDs is currently permitted, so this does not require populating 1,600 live triggers. The frame is rejected and the companion/session fails despite no command-count or pending-count overflow.

The serialization sizes were independently computed with Node 22.20.0; no network load was generated. Minimal repair: emit cancellation acknowledgement metadata with command sequence and counts instead of echoing the ID arrays. The cancellation command itself must retain all IDs; Node's ordered `applied` receipt already provides the tombstone-pruning boundary. Alternatively, enforce a real serialized-byte limit on every receipt batch, including single-row oversize handling. Retaining the full node-ID array can reproduce the same amplification and also needs a byte bound.

## Ordering and failure properties supported by source inspection

- The worklet checks frame/wall continuity and the old producer lease before applying buffered commands. An expired heartbeat cannot revive the same session. A clock discontinuity permanently fails the companion rather than adjusting deadlines or falling back to Node timers.
- The ordered receipt queue puts prior-block onsets before a later cancellation/stop `applied` acknowledgement. Node retains bounded cancelled-pending tombstones until that boundary, records an already executed onset arriving after cancellation, and does not recreate its active voice. A same-block cancellation removes pending work before onset processing. This ordering is consistent with the interface contract.
- Node admission bounds pending plus tombstones at 5,376. Worklet pending, voices, objects, commands, receipt queue, unacknowledged commands, socket buffering, and acknowledgement age each have explicit bounds. RC-02 concerns the composition of those bounds with message size.
- The private sink requires a fresh 256-bit process capability and the exact local bridge origin; producer and sink paths differ. The page also requires the capability. No capability is included in the public diagnostics. CLI construction explicitly enables the companion; the two-argument exported bridge remains labelled as the legacy Node-timer diagnostic path.
- Execution receipts retain callback wall time, render frame, within-block sample offset, execution-time coordinates, and receipt arrival separately. Calibration uses independent render callbacks. Runtime maximum residual, coarse wall-clock precision, one quantum, and Node wall/monotonic drift contribute to the stated uncertainty. A zero-gain route makes this control scheduling evidence, not audible or hardware presentation evidence.

## Subsequent idle failure and measurement-model derivation

`clean-verification-idle-failure.json` preserves a later actual failure of that same model during clean verification. Independent arithmetic confirms a signed frame/wall residual of -3.999755859375 ms, base terms totaling 6.06107585416667 ms, and the reported total 10.060831713541669 ms. Frames remained consecutive; the current and previous callbacks had the identical millisecond wall reading. There was no active session or pending work. The most recent Node pair was 81 ms before the fatal callback and its wall-offset estimate was **+0.99609375 ms** versus the initial pair. Subtracting that updated offset would enlarge this particular residual to approximately -4.99585 ms; the evidence does not justify explaining this failure away as common UTC drift.

There is, however, a distinct algebraic issue in the model, independent of whether a new run will pass. For the explicitly defined control witness, let all times be milliseconds, `h = 1000 / sampleRate`, `W` be observed callback wall time, `N` the frozen Node wall offset, `C` the fixed frame/wall mapping, `T` the intended Node time, and `F` the callback's first frame. For a normally scheduled target `q = ceil((T + N - C) / h)` with sample offset `k = q - F`, the reported observed control time is `A = W + k*h - N`. Therefore:

```text
A - T = (W - F*h - C) + (q*h - (T + N - C))
      = observed mapping residual + sample-rounding error
```

When a late target is clamped to offset zero, that additional lateness also appears in `A - T`. The mapping residual therefore already contributes to the measured scheduling error. It is not a separate error term in converting the independently observed `W + k*h` witness through `N`. Adding its lifetime absolute maximum again to that timestamp's measurement uncertainty double-counts scheduling displacement. Separating it into a clearly labelled mapping diagnostic and independent stability guard is mathematically defensible for this control scope, while retaining the actual ±20 ms drop rule, the ≤10 ms measurement-uncertainty gate and the conservative observed-error-plus-uncertainty test.

The conversion still needs conservative Node wall-pair uncertainty, wall-offset change, coarse worklet Date allowance and the full-quantum allowance for the defined within-block witness. Later Node pairs' brackets matter: a pair preempted between its monotonic reads can be wider than the initial pair. Using only the initial pair width plus midpoint drift can miss that uncertainty. A safe bound retains the maximum observed pair uncertainty as well as the observed offset change, or an explicitly derived interval envelope. Maximum **observed** wall drift remains empirical; an arbitrary unseen UTC step between sampled pairs is not ruled out by elapsed pair age alone. Raw brackets, pair timing/age and discontinuity guards must remain inspectable.

This derivation is design review, not a source or live-run pass for the revised model. It does not supply a physical presentation timestamp, fix the unmeasured producer audio-to-performance relationship, justify retargeting already queued controls, or retroactively turn the preserved failed runs into passes.

## Native worker scheduler hypothesis — pre-probe design review

Step09 explicitly qualifies control/event delivery to a test receiver and reserves actual spatial sound forM2. A dedicated Node worker that owns pending deadlines, positions, test voices and actual execution can satisfy that scope in principle. Its witness must identify `node-worker-control` and timestamp a real worker-side state mutation; it must not populate fictitious audio frame, sample offset or rendered-sample fields. This is a proposed measurement architecture, not a proven timing improvement or permission to reinterpret earlier failures.

The worker would avoid the parent JavaScript event loop and UTC conversion. `process.hrtime.bigint()` provides a high-resolution interval clock unrelated to time of day, but a timer callback is still subject to host scheduling. Node expressly does not guarantee exact timer timing/order and truncates fractional delays. Therefore every wake must reread the actual clock, reschedule if early, and apply the unchanged late-drop policy if too late. [Node process clock documentation](https://nodejs.org/api/process.html#processhrtimebigint), [Node timer documentation](https://nodejs.org/api/timers.html#settimeoutcallback-delay-args).

The bounded probe should discriminate these scenarios before any application architecture changes:

- Independently bracket a parent `performance.now()` read by two `hrtime.bigint()` reads. Preserve every raw tuple and numerical allowance, including deliberately widened brackets. Keep nanoseconds as BigInt/raw decimal strings; subtract a BigInt anchor before conversion to Number. Validate cross-thread epoch compatibility with parent-send ≤ worker-observe ≤ parent-receive hrtime values and held-out calibration brackets. Using the same incorrect offset for deadline conversion and inverse receipt conversion can produce near-zero reported scheduling error, so scheduling results alone cannot validate this mapping. An injected wrong offset must fail the independent interval checks.
- Distinguish a trigger acknowledged in the worker before a100/250ms parent stall from one admitted only after the stall. The former tests isolation; the latter must retain its actual ingress lateness and cannot be backdated. Separately stall the worker itself, preserving late drops and no catch-up burst, and retain an independent host scheduling witness. Parent isolation is not protection against whole-process/host descheduling.
- Timestamp each actual voice insertion/removal with a before/after hrtime bracket and receipt sequence. Reusing a callback-entry timestamp for a long batch could hide late mutations. Snapshot the execution-time position. Keep intended deadline, worker admission, worker mutation, ACK and parent receipt distinct.
- Give one ordered command port a clear application boundary. Parent `postMessage` is not a remote cancellation ACK. Test cancellation before worker application, cancellation racing a due timer, stop followed by a new epoch, already-executed receipts delayed until after cancellation, and a never-executed cancelled ID injected after its ACK. Earlier execution receipts must precede the `applied` boundary; parent tombstones must not revive voices. Retain existing namespace and object-rebinding regressions.
- Make the worker own its500ms lease and voice expiry. Check an expired lease before draining queued stale heartbeat/trigger messages, and retire the expired session so backlog cannot revive it. Test a blocked/dead parent, a failed/terminated worker and restart. Bind messages to a worker incarnation; restart requires a fresh producer session, not replay of the old queue.
- Bound commands and receipts by both unacknowledged count and bytes, with explicit credits/ACKs. `postMessage` is not a writable-stream backpressure interface. Test a parent that stops draining receipts, a burst at pending capacity, malformed internal messages, sequence gaps and `error`/`exit`/`messageerror` paths. Saturation must fail visibly and release state. Avoid console or file operations in the deadline path: Node documents that worker stdio can block behind a synchronously blocked receiving thread. [Node worker stdio documentation](https://nodejs.org/api/worker_threads.html#synchronous-blocking-of-stdio).

A successful isolated probe would justify considering a narrowly scoped receiver implementation and generalized witness type. It would not qualify integrated F01/F04 delivery, the producer audio-to-performance boundary, two-minute count/timing gates, physical audio or human checks. Those require their own fresh source-bound evidence. This reviewer launched no worker, browser or load test for this proposal.
